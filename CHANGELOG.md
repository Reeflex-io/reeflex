## [Unreleased]

### Changed

- **Every dependency this repo declares is now bounded ABOVE, and a CI check refuses a new open floor (the sweep PR #123 asked for).** #123 fixed one package and closed with *"Not fixed here: every other package with an unbounded dependency floor. Worth a sweep."* This is that sweep. The defect it generalises: `reeflex-holds` declared `mcp>=2`, `mcp 2.1.1` arrived, and an SDK **minor** changed what our users see — a holds operator could no longer tell a typo from an outage — on a commit that touched none of this repo. `main` went red on PR #112, which changed no file in the package.

  **Six open floors were found and closed.** Each ceiling is justified by the API surface this repo actually uses from the dependency, with the reasoning in a comment beside the pin:

  | where | was | now | the surface that justifies the ceiling |
  |---|---|---|---|
  | `reeflex-mcp` | `pyyaml` *(no floor, no ceiling)* | `pyyaml>=6,<7` | `yaml.safe_load`, `yaml.YAMLError`, `yaml.safe_dump(sort_keys=…, default_flow_style=…)`.   **Nothing that resolves today changes.** The pins are ceilings, not downgrades: with them in place `reeflex-mcp` still resolves `mcp 1.30.0` / `PyYAML 6.0.3` / `anyio 4.15.1`, and the suites are unchanged — 342 / 81 / 286 passed for `reeflex-mcp` / `reeflex-holds` / `reeflex-claude`.

  **Two open floors were found inside the instruments, which is worse than in a package.** `gate.py` installed a bare `pytest` into every suite venv, so the tool that judges whether the tree is healthy re-resolved itself on every run; and `.github/workflows/ci-reeflex-mcp.yml` did the same. Both are now `pytest>=8,<10` — the range measured green on all three suites at **both** ends (8.4.2 and 9.1.1) rather than a guess.

  **And two on the release/publish path.** `release.yml` ran `pip install --upgrade build` — an instruction to take the newest thing on the index, on the one workflow whose output is the artefact a customer installs; it now reads `.github/requirements-build.txt` (`build>=1.2,<2`). `docs.yml` ran `pip install "mkdocs-material[imaging]" mkdocs-git-revision-date-localized-plugin`, two open floors on a workflow that **had no `pull_request` trigger**, so an upstream release there could only ever be discovered by turning `main` RED. Pinned in `.github/requirements-docs.txt`, and see *Added* for the trigger.

  **`reeflex-core` has no dependency floor to pin, and that was measured rather than assumed.** It declares no dependencies at all (no `pyproject.toml`, stdlib-only by contract — the `Dockerfile` says so and `docker build` installs nothing), so the sweep found nothing to bound in it. Named here because "we checked and there was nothing" is a different statement from "we did not check", and the check reports on all eight packages.

- **The daily PyPI smoke tests what is PUBLISHED, so it cannot catch a bug before customers can.** `smoke-pypi.yml` installs `reeflex-mcp` / `reeflex-holds` / `reeflex-claude` from PyPI — never from the tree — and invokes each entry point. That is the right instrument for the failure it was built for (an upstream release breaking a *published* package with no commit here, e.g. `mcp 2.0.0` on 2026-07-28) and it is the wrong instrument for reading a release as healthy, for three reasons, stated here so nobody mistakes a green smoke for a verified release:

  1. **It measures the published version, so a defect in the code being released is invisible to it until after the publish.** A green smoke on the day of a tag is a statement about yesterday's artefact.
  2. **It asserts `--help` exits 0.** That catches import-time death and nothing else. A core that fails to *refuse*, or a holds tool that masks the reason a call failed (#123 exactly), exits 0 on `--help`.
  3. **`reeflex-core` is not in its matrix, because it is not on PyPI.** `pypi.org/pypi/reeflex-core/json` has exactly one release — **`0.0.1`, uploaded 2026-07-04** — and `release.yml` builds sdists and wheels for the other three only. So `pip install reeflex-core` gets a July name reservation, not 0.2.0, and the package that *is* the decision engine gets no PyPI smoke at all. Its published artefact is the GHCR image (`ghcr.io/reeflex-io/reeflex-core:v0.2.0`, byte-identical to `:latest`).

  **The near-miss that makes this concrete rather than theoretical.** `reeflex-holds 0.2.0` went to PyPI at **2026-09-07T14:58Z** carrying #123's `mcp<2.2,>=2`. `mcp 2.2.0` was published at **16:06Z the same day** — **1h08m later**. The ceiling landed in the published wheel with just over an hour to spare, and on the pre-#123 metadata that release would have resolved `mcp 2.2.0` on any fresh install from that afternoon onward. The published `reeflex-mcp 0.1.3` still declares `['mcp<2,>=1.2', 'pyyaml', 'anyio>=4.5']` today, so two of the floors this entry closes are live in front of customers until the next publish.

  **Independent measurement of the published 0.2.0 is qa's, and it is in flight rather than done.** The standing finding on this class is `code-reports/qa--035--20260907-1740--the-gate-is-green-on-an-artefact-nobody-can-run.md` (the release gate reading green over an artefact no customer could run). qa round **204** is measuring the published 0.2.0 as this lands — a fresh-venv install from PyPI plus the RFX-97 probe against a core started from the package, i.e. *does it refuse*, not *does it start* — and its report will land beside that one under `code-reports/qa--0NN-*`. This entry does not borrow its conclusion; point 3 above is what the console can already act on, and it means qa's `reeflex-core`-from-PyPI leg has no artefact to run against.

### Added

- **`scripts/check_dependency_floors.py` + a `dependency floors` CI check.** Static, no network, no installs: it walks every dependency manifest in the repo (`pyproject.toml`, `package.json`, `composer.json`, `requirements*.txt`/`constraints*.txt`) and fails on any requirement with no upper bound. It runs three ways — as its own fast job in `gate.yml` (~20s, its own check name on the PR page), as two `gate.py` components (`dep-floors-selftest`, `dep-floors`) so a local gate run sees it too, and as 25 unittest cases in `scripts/tests/` under the runner that root is actually discovered with (RFX-87). **A new package is covered by glob the moment it lands** — no list to update, which is the RFX-216/RFX-217 defect shape this deliberately avoids.

  **Three things stop it from being the wrong instrument, the class that has cost this repo three defects this month.** (1) The anchored manifest reader is **cross-checked against stdlib `tomllib` on every `pyproject.toml`** whenever the interpreter has it (CI runs 3.12); a disagreement is a FAILURE naming the file, not a quiet fallback. (2) A manifest shape it cannot read — a Poetry-style dependency table, say — is a FAILURE, because an instrument that cannot measure a file must never report PASS over it. (3) It has **a floor under its own walk**: "nothing unbounded was found" is a claim an empty walk satisfies, so it refuses to pass below `MIN_REQUIREMENTS` and prints the count it measured (17 requirements over 7 manifests today) on the verdict line of every run — the RFX-217 lesson, applied to a new check rather than learned again. Proven in both directions: the checker **FAILS on the tree as it was before this change**, naming all six floors, and that control is a test rather than a paragraph.

  An allowance requires a reason **and** a ticket reference, is printed in full on every run, and an allowance whose target no longer exists is a FAILURE — so it cannot rot into standing permission for a file nobody declares any more.

- **`Docs` now runs on pull requests (build only, never deploy).** The workflow that publishes `docs.reeflex.io` had `push`/`workflow_dispatch` triggers and nothing else, so a docs regression could only be discovered by turning `main` RED — which had already happened once (fixed forward through #128, and recorded as still-open by dev-3 round 039). A PR now builds the docs with `--strict`; the CNAME step, both Pages steps and the whole `deploy` job are gated on the event, so a pull request can never publish. Added in the same change that pins the docs build's dependencies, precisely so that pin is verifiable before it merges rather than after.

- **`reeflex-litellm` 0.1.0 — a Reeflex seat inside an LLM gateway (RFX-236, epic RFX-235).**

  A [LiteLLM](https://github.com/BerriAI/litellm) post-call guardrail that builds one Action Envelope **per tool call** on every response a model returns through the proxy, asks `reeflex-core` `/v1/decide`, and then releases the call, removes it, or withholds the whole response while a human decides. One integration at the gateway covers every agent behind it; no per-application instrumentation.

  **Not a second classifier.** Axes, verb, magnitude, danger signature and tier all come from `reeflex_claude.classify` — the one classifier every Reeflex adapter shares — and the envelope is `reeflex_claude.envelope.build_envelope()` with a gateway-identity **overlay** on top (`agent.id` = `agent:litellm-gateway/<model>` per RFX-138, `action.namespace` = `litellm-gateway`, `action.ability` = `litellm/<gateway tool name>`, `agent.session_id` namespaced `litellm:` so it cannot collide with another seat's in R5's session ledger). What this package adds is the **NORMALIZE** step a gateway needs and the other seats do not: a gateway does not know its tool names, so `run_shell` / `execute_command` / `acme_infra_runner` have to be expressed in the classifier's vocabulary, on name **and** argument shape, with an operator override in `REEFLEX_LITELLM_TOOL_MAP`. A mapping that is not faithful is not made: `delete_file(path=…)` is left unmapped rather than rewritten into a synthetic `rm -- <path>`, because fabricating a command the model never proposed would put that command into the line a human reads in the audit record (RFX-144/145/146). An unmapped call goes down the classifier's unknown-tool path, which measures as `require_approval` under `reeflex.policy/irreversible_broad_prod` — it **asks a human**; it is not allowed and not silently denied.

  **The four outcomes, walked live through a real proxy against the published `ghcr.io/reeflex-io/reeflex-core:v0.2.0` image and asserted on the bytes the caller received.** `allow` → the tool call, untouched. `deny` → the call **removed** from `tool_calls`, `finish_reason` flipped to `stop`, a structured refusal in `message.content`, and the command string absent from the response bytes. `require_approval` → the response is **withheld** (measured: 1.10 s while a real verified human approved, then released; 1.11 s to a rejection; 30.1 s to a timeout that names the still-open hold so the caller can retry). Core unreachable/unparseable/answering something unknown → **fail closed**, `reeflex_unavailable` / `reeflex.core/fail_closed`, with the reason in the payload the model reads. A response carrying several tool calls is ruled on per call: one denied beside one allowed removes exactly one. A response with **no** tool calls is returned byte for byte unchanged and never sent to core, so with core down text still flows and actions do not.

  An approved hold is **never** released on the hold status alone — the original envelope is resubmitted and released only if core allows it, because core's eight resubmission checks are the authority and one of them (RFX-138) exists precisely because a hold id by itself was once enough to spend somebody else's approval. Getting that resubmission accepted needs two facts that pull against each other, both measured: the envelope must be the **same** one the human approved (checks 5/7/8 compare the hashed projection, the decision inputs `params` omits, and the whole `agent` block) while the nonce must be **different** (`envelope._check_nonce` is a hard `400 replay: nonce already seen`). `canonical_hash()` excludes `meta`, which is why both can hold at once.

  **What the seat does NOT do, stated in the package README before the install instructions.** It sees a tool call **PROPOSED, not EXECUTED** — it removes an instruction before the application is handed it, and an application that ignores the refusal is **not stopped**, because the gateway is not in the execution path. Every refusal therefore carries `"stage": "refused_at_gateway"` as part of the payload contract (SPEC §5.1 adapter obligation): an evidence pipeline that collapses that into an execution-side prevention is claiming a guarantee this seat cannot deliver. No prompt reading, no PII masking, no content scoring — the hook reads `tool_calls` and nothing else, and zero-LLM in the decision path is recorded as a **limit**, not as marketing.

  **Two known holes, both measured rather than assumed, both named as follow-up tickets.** (1) **Streaming is not governed by this hook**: `mode: post_call` fires for a buffered response, and with `stream: true` the identical `rm -rf /` tool call reaches the caller intact as `chat.completion.chunk` deltas. Refuse `stream: true` at the gateway until the streaming-iterator hook is implemented. (2) **Tenancy is not implemented**: a gateway virtual key or team is not mapped to a Reeflex org, and with no `x-reeflex-session` header and no OpenAI `user` field R5's cumulative session budget is scoped to a **single request**.

  **Latency, measured in the gateway** (LiteLLM 1.100.0, core v0.2.0 with 32 decision workers, off/on requests fired alternately at two otherwise-identical proxies, 200-request warm-up, repeats per cell, zero errors in every cell). Added p50 per request: **+80 ms at 1 concurrent** against 82 ms measured for `POST /v1/decide` on its own — the seat costs one decision and the adapter's own overhead is in the noise. **+170 ms at 10 concurrent on a single-worker proxy, +85 ms with `--num_workers 4`** — the extra was the proxy's own GIL contention, not the seat, and scaling proxy workers is the operational note. **+850 ms / +570 ms at 50 concurrent** where the constraint is decision capacity: core sustained ~195 decisions/s at that concurrency with `shed_total: 0`, so scale `reeflex-core` before scaling anything in this package. A response with N tool calls costs about N decisions (+158 ms measured for two) because calls are decided **in order, not concurrently** — R5's cumulative budget is charged per decision on a shared session, so concurrent decisions would make the verdict depend on which one reached the ledger first.

  Ships with a mock model (`proxy/mock_model.py`) that returns the tool calls you name in the prompt, two proxy configs that differ only in whether the guardrail is present (the latency control), `bench/latency.py`, and a `reeflex-litellm normalize` CLI for checking a tool map with no network. Wired into `gate.py` (`pytest-litellm`, plus `reeflex-litellm/tests` in `SUITE_ROOTS`) and into `scripts/check_test_census.py`. Not added to `PUBLISHED`: publication is an owner gate.

### Changed — BREAKING

- **`REEFLEX_REQUIRE_VERIFIED_APPROVER` now defaults to `true`, and `reeflex-core` is `0.2.0` because of it (RFX-84, RFX-97).**

  **What changes.** `POST /v1/holds/{id}/resolve` refuses an approver core cannot tie to the credential the request was made with. Out of the box — no `REEFLEX_RESOLVER_TOKENS`, no flag — resolving a hold now returns `403 principal_not_verified` instead of recording the caller's asserted principal as the human who approved it.

  **Who this breaks.** Anyone running the OSS core (or the published image) with **self-asserted approvals**: no `REEFLEX_RESOLVER_TOKENS` map configured, and holds resolved by whatever principal the request body names. On upgrade every hold resolution starts failing `403 principal_not_verified` — the holds API, `reeflex-holds` (CLI and MCP), the WordPress *Pending approvals* screen, the n8n approval loop, and any custom resolution tooling. `/v1/decide` is untouched: no verdict, rule id or reason moves, and a deployment that already sets `REEFLEX_RESOLVER_TOKENS` sees no change at all.

  **The one-line escape hatch**, for someone who genuinely needs the old behaviour while they wire up verification:

  ```bash
  REEFLEX_REQUIRE_VERIFIED_APPROVER=false
  ```

  That restores 0.1.x exactly: holds resolve on the caller's word, core warns on stderr, and the hold record, the `hold.resolved` webhook and the Art. 14 audit line carry `decided_by_verified: false` / `principal_source: "asserted"` so nothing downstream can mistake it for a verified decision. **The real fix is `REEFLEX_RESOLVER_TOKENS`** — bind each approver's bearer token to the principal it *is* (`{"tok_live_alice": {"type":"human","id":"alice@example.com"}}`, inline JSON or a file path, re-read per request so no restart is needed).

  **Why.** RFX-84, measured live: one bearer token raised an irreversible + broad + production hold, approved it as `human:totally-invented-auditor`, and rode that approval to `allow` — and core **minted and persisted** the record saying a named human had exercised oversight. PR #90 made the approver *verifiable* but left the default off, on the argument that defaulting it on would make every hold unresolvable on upgrade. That argument was about upgrade cost, and this entry is that cost being paid explicitly rather than the defect being kept. Measured on a built image with the RFX-97 release gate at `7f9ebf8`: at the old default 5 of 6 known evasions close and the survivor is exactly this one; at the new default it closes. Shipping an artefact whose **default** accepts an invented approver, in a product whose entire claim is evidence of human oversight, is the fail-open class the last six tickets were spent killing.

  **The refusal tells the operator what to do.** `principal_not_verified` on its own sends someone to the source, and the person reading it is usually a human who just clicked *Approve* on an action that is now stuck. The 403 now names the principal it would not accept and states what would change the answer, in prose (`reason`) and in fields a dashboard can render (`remedy`: `principal`, `why`, `actions[]`, `docs`). Two situations, one code, two different next moves: a credential missing from a map that **exists** (`why: "unbound_credential"`) is told to add it; a deployment with **no** map (`why: "verification_not_configured"`) is told both the fix and the escape hatch. `remedy` is additive — `error`/`reason`/`hold_id` are unchanged, and every existing consumer ignores unknown keys.

  **Parsing is tri-state, and unset is no longer the same as false.** `true|1|yes|on` → on; `false|0|no|off` → off; **unset, empty, or anything unrecognised → the default, which is now on.** A guard that switches off on a typo (`="False "`, `="maybe"`) would be this exact fail-open shape one config file over, so only an explicit recognised falsey word opts out.

  **What in our own tree depended on the old default, checked before the flip and fixed here.** All four WordPress live-core harnesses (`conformance-demo`, `admin-holds-demo`, `fanout-regression-demo`, `hold-dedup-regression-demo`) resolve real holds and sent no `Authorization` header — measured, all four fail against a default core. They now present a credential bound to the principal each scenario approves as, looked up from `reeflex-wordpress/tests/harness-resolver-tokens.json`; the CI gate starts its core with `REEFLEX_RESOLVER_TOKENS` pointed at that **same file**, so the two sides cannot drift. Deliberately not the opt-out: the gate has to exercise the configuration we ship, or the default is tested by nothing. `conformance-demo.php`'s **H10 is why the map contains an `agent:wordpress` entry** — verification (check 4) runs before four-eyes (check 5), so without a credential bound to the raising agent's identity H10 would be refused `principal_not_verified` and never reach the guard it exists to prove; it asserts the *reason*, not just the 403. `test_hil.py`'s resolve tests were likewise given bound credentials rather than the opt-out, for the same reason. Ten core tests moved; 407 pass. Docs updated: `docs/reference/configuration.md` (new *Verified approvers* section), `reeflex-core/README.md`, `reeflex-holds/README.md`, `docs/guides/n8n.md`, the demo3 approval-loop README, `docker-compose.yml` and the `Dockerfile`. QUICKSTART resolves no holds and is unaffected.

  **A defect the flip surfaced, fixed here because the default makes it blocking: with `REEFLEX_AUTH_TOKEN` set, a deployment could bind only ONE verified approver.** `server._authorized()` compared the bearer against that one shared string, so every approver credential in `REEFLEX_RESOLVER_TOKENS` except the one that happened to equal the gate token was refused `401` at the door — before reaching the verification it was created for. An authenticated deployment therefore could not have two verified approvers, which is to say it could not have four-eyes at all. Latent while verified approvers were opt-in; on the default path the moment the default flips. A bearer that `REEFLEX_RESOLVER_TOKENS` binds to a principal is now accepted as authenticated **on the hold-resolution route only** — it is a secret the operator issued for exactly this purpose, and it names who it belongs to, which is strictly more identifying than the shared token it is accepted alongside. It is **not** a key to `POST /v1/decide`: the party that approves actions and the party that submits them are different roles, and this default exists to keep them apart. Measured before and after against the built image (`reeflex-core/tests/test_hil.py::TestResolverTokenIsAlsoAuth`, four cases including the two negatives).

  **The instrument could not measure the artefact at this default, and that was fixed before the tag rather than caveated in it (RFX-179).** When the flag flipped, the RFX-97 release-gate probe held one bearer token, so at the new default its A3-self, A3-fab and A6 rows were refused `principal_not_verified` *before reaching the guards they name* and scored `INCONCLUSIVE` — and `INCONCLUSIVE` was in neither term of the exit code, so the runner printed `still exploitable: none` and exited 0 over three attacks that never ran. The honest reading of the flag-on run was therefore "4 of 6 closed, 3 not attacked", and the six-of-six claim could only be assembled from two runs at two configurations, which is exactly the stitched-together evidence the canon exists to stop. Fixed in #112, below.

- **An action the canon cannot CLASSIFY now resolves to a hold, under its own rule id, instead of a terminal deny (RFX-132).** After #89 and #90 the three conservative defaults compose: `reversibility → irreversible`, `blast_radius → systemic`, `environment → production` is exactly R3 — the one rule a human is not allowed to clear. So the envelope an adapter emits when it *cannot price an action* (`{"action":{"verb":"frobnicate"},"target":{"environment":"qa-eu"},"axes":{}}`) was getting a hard refusal with no human anywhere in it, on a product whose value proposition is the human in the loop. Each default that produced it was individually right; the composition was never designed.

  **The decision, and the argument you can attack.** DENY makes the product brittle at the moment it is least certain, and a gate that refuses the unfamiliar gets switched off — which is a fail-open with extra steps. ALLOW is the defect class the last six tickets were spent killing. HOLD is the third state Reeflex exists to have, and "I do not know what this is, ask a human" is the most honest thing the product can say about an input it cannot verify.

  **New R0**, `reeflex.policy/unclassified_action`, highest precedence. `envelope.py` now records, per field, whether the caller **declared** a value core recognises or core **guessed** one — a core-computed `provenance.undeclared` list — and R0 fires when a verdict R2 or R3 would have produced rests on at least one of those guesses. The reason names the fields, so the hold says *what* could not be classified rather than only that something could not.

  **Four bounds, each one measured rather than asserted.** (1) **R0 only ever converts a refusal.** It fires when R2 or R3 would, never on an allow, so the long tail of unaliased verbs on reversible non-production actions stays `default_allow` — which is the volume objection, and RFX-145's lesson from the other side. (2) **Only the three inputs R2/R3 actually read can trigger it** (`axes.reversibility`, `axes.blast_radius`, `target.environment`); guessing `axes.externality` or `action.verb` is recorded but softens nothing. (3) **"Declared" is judged on the FOLDED token**, so `Systemic` is a declaration of systemic — judged on the raw exact match a caller would downgrade a terminal deny to a resolvable hold by capitalising one letter, which is RFX-86's evasion one tier up. (4) **`provenance` is core-computed and overwritten unconditionally**, so a caller cannot assert its way from R3's deny into R0's hold; that is the whole security of the rule and it has its own test.

  **The coercion itself is deliberately unchanged.** `_AXIS_ALLOWED` is still matched exactly, so `Broad` still coerces to `systemic` as it always did. Folding the *value* too would turn `blast_radius: "SINGLE"` on an irreversible production action from a DENY into an ALLOW, and a case fix that relaxes a refusal is not this ticket's to make. The residual wrong-DENY is stated in `envelope.py` and left as its own ticket.

  **Measured volume, because "HOLD not DENY" is only defensible if the holds land somewhere an operator can keep up with.** Over a 31-action corpus of what a coding agent actually issues, driven through the *shipped* `reeflex-claude` classifier and envelope builder: **0 of 31 envelopes carry a guessed classification**, so R0 adds **zero** holds to a realistic workload — both reference adapters always emit all three axes and a declared environment. Over the exhaustive 6,048-input grid (756 axis/verb/env combinations × 8 provenance shapes), **294 decisions move (4.9%), in exactly two directions**: 147 `deny/irreversible_systemic_prod → require_approval/unclassified_action` (the ticket's target) and 147 `require_approval/irreversible_broad_prod → require_approval/unclassified_action` (a relabel; same verdict, same obligations). **No allow becomes a hold, no refusal becomes an allow, and 0 of the 756 grid points a CONFORMANT adapter can produce move at all.** Harness and transcripts: `code-reports/dev-3--028-evidence/`.

  **R0 is resolvable, which is the entire difference from the R3 it replaces.** `irreversible_systemic_prod` stays in core's `NON_RESOLVABLE_RULES`; `unclassified_action` is not in it, and the default resolution policy makes it human-only. `reeflex-spec/SPEC.md` §4.0 states the rule normatively, including the adapter SHOULD that keeps R0 rare.

- **A budget dimension no longer prices an unbounded action as the smallest possible one (RFX-143).**

  `magnitude.count` is an integer `>= 1` with no member meaning "I cannot enumerate the affected set", and an absent count was filled with `1` — the *minimum* of its domain — under the comment "conservative default". Every dimension in `budgets.rego` charges that number and `objects_touched` charges it on every action, so R5's deletions budget was measuring the caller's candour rather than its deletions. Measured on `759b83f`, one session, `irreversible`/`scoped`/`production`, R2 and R3 unable to fire:

  ```
  ONE call, count=45         -> require_approval  session_delete_budget
  ONE call, count=1          -> allow
  ONE call, magnitude absent -> allow   (and 20 more before a human is asked)
  ```

  **What changes.** Each dimension now charges `max(magnitude.count, count_floor[axes.blast_radius])` — a count may raise the charge above the floor its own blast radius implies, never lower it. `count: 1` next to `blast_radius: broad` is a self-contradiction (SPEC §4 defines `broad` as "a large set / whole table / bucket") and the fail-closed reading of a contradiction is the larger one. Core also now records the fill: `magnitude.count` joins `provenance.undeclared`, the block it always belonged in — its own docstring says "anything a rule reads to decide WHAT KIND OF ACTION this is belongs here".

  **Who this affects.** Repeated recoverable deletes under one session, trip point before → after: `single` 21 → 21, `scoped` 21 → 21, `broad` 21 → 12, `systemic` 21 → 2. `single` and `scoped` are floor `1` in the shipped pack *deliberately* — those values assert a bounded set, and `scoped` is what the reference adapters emit for ordinary work, so flooring it would retune every everyday session instead of the unbounded ones. No verdict changes for any caller that states a count at or above its axis floor.

  **What is NOT fixed.** `ledger.py` records the raw `magnitude.count`, so the floor applies to the action being decided and not to the history it is compared against — which is why `broad` lands on 12 rather than 3. The floors are policy data in `budgets.rego` next to the limits, and are illustrative defaults an operator must review. See SPEC §4.1.2.
- **The holds surface no longer answers a word it does not know with a confident wrong answer (RFX-211, RFX-218, + two siblings found with them).** `GET /v1/holds` is the call that answers *"what is held?"*, and every one of its parameters used to degrade rather than refuse. Measured on `759b83f` with three real holds in the store — **16 of 16 arms** gave a wrong answer, and each is now a named `400`:

  | request | before | now |
  |---|---|---|
  | `?status=all` | `200 {"items":[],"count":0}` | `200`, the full set (explicit synonym for no filter) |
  | `?status=resolved` / `Pending` / `pending ` / `banana` | `200 {"items":[],"count":0}` | `400 status: unrecognised`, naming the accepted set |
  | `?cursor=<bogus>` | `200`, **page 1 again**, silently | `400 cursor: unknown` |
  | `?limit=banana` / `0` / `-5` | `200`, limit silently 100 / 1 / 1 | `400 limit: …` |
  | `holds.resolve_hold(id, "approved", …)` | hold **rejected**, silently | `ValueError`, hold untouched |

  **Why the read half matters.** No action gets through — this is the instrument, not the gate — but it is the instrument human oversight depends on, and it could report zero when the answer was not zero. `all` and `resolved` are not invented near-misses: both are **valid vocabulary on the Reeflex portal's own holds API** (which `422`s an unknown status), and the published `reeflex-holds` MCP `list_holds` tool forwards `status` **with no validation of its own** — so an agent asking what is held could get an empty list and reasonably report "nothing is pending" while holds were pending. RFX-65's month-long invisible pending holds are the precedent: something has to look, and a lookup that answers "nothing" to a typo is worse than one that errors. The two surfaces still do not share a vocabulary (`resolved` is the portal's word; `approved`/`rejected`/`consumed` are core's), which is why the refusal names the set it checked against instead of guessing.

  **Why the write half matters.** `resolve_hold()` implemented `new_status = "approved" if decision == "approve" else "rejected"`, so the literal its own docstring documented (`"approved"`) fell to the else branch and **rejected** the hold — no error, and a return value indistinguishable from a human's deliberate rejection. A later resubmission then denied with `reeflex_hold_rejected`, which reads as *"the human said no"*: an Art. 14 oversight record saying a hold was rejected when the integration meant to approve it. **Not reachable from the wire** — `server.py` and the published `reeflex-holds` client both validate `approve|reject` first — so this closes the in-process path and any future caller that trusts the docstring. It raises rather than also accepting `"approved"`, because a two-valued parameter whose second arm is *"everything else"* is the defect, not the particular spelling that hit it.

  **The cost, stated.** A `cursor` can legitimately fall out of a *filtered* result set between pages (page with `status=pending`, and the hold at the cursor gets approved). That now errors rather than silently restarting at page 1. Erroring is the deliberate choice — a caller told its cursor is stale can restart on purpose, whereas a silent restart re-serves rows it already processed and can loop forever — and the two cases carry distinguishable messages. `--status all` is now also accepted by the `reeflex-holds` CLI, for the operator who learned the portal's screen.

  **The guard is a partition, not an inventory.** `HOLD_STATUSES` is not hand-maintained: `test_holds_vocabulary_rfx211_rfx218.py` drives every state transition `holds.py` implements, collects the statuses actually written, and asserts the observed set **equals** the declared one — so a sixth status fails the suite until it is declared, and the API then accepts it. That shape is deliberate: qa--018's finding on RFX-87 is that a sound assertion pointed at a short inventory is green about the value it never looked at. 22 tests, `unittest.TestCase` (a pytest-style file here collects **zero** tests under the gate and still reports OK — RFX-87). All six behavioural lines of the fix were reverted one at a time and the suite went red for each (`scripts/bite-check-rfx211-rfx218.py`).

  **No decision path, policy or rule changed.** `/v1/decide` is untouched; no verdict, rule id or reason moves.
